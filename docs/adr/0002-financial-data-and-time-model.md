# ADR 0002: Model money, dates, and financial history explicitly

- **Status:** Accepted
- **Date:** 2026-08-08

## Context

Financial reminders become untrustworthy if amounts are rounded, due dates shift
with time zones, or historical state is overwritten. The MVP is limited to
fixed monthly INR commitments, but its storage decisions should not prevent
future currencies, payment evidence, or variable amounts.

## Decision

Use PostgreSQL as the system of record. All schema changes are versioned Flyway
migrations committed with the application. Hibernate/JPA mappings must conform
to the database schema; automatic schema creation and update are disabled
outside disposable local environments.

### Core data model

| Entity | Responsibility |
| --- | --- |
| `users` | Account identity, preferred IANA time zone, and lifecycle state. |
| `commitments` | The ongoing obligation: title, category, fixed expected amount, payment mode, recurrence, and lifecycle state. |
| `payment_occurrences` | One expected due payment created from a commitment. It keeps the original expected amount and due date. |
| `reminder_rules` | A user's timing and delivery preference for a commitment. |
| `payment_records` | Later proof of a payment; it does not overwrite the expected occurrence. |
| `audit_events` | Append-only record of material user and system actions. |
| `idempotency_keys` | Records a completed mutating request and its response identity, preventing duplicate creation on retries. |

### Money

- Store every amount as `amount_minor BIGINT` and `currency CHAR(3)`.
- The MVP accepts `INR` only, where `64900` represents INR 649.00.
- Do not use floating-point types or PostgreSQL's locale-sensitive `money`
  type.
- Expected amounts must be non-negative and fit in a signed 64-bit integer.

### Dates and time

- Store a user's IANA time zone, for example `Asia/Kolkata`.
- Store a recurring payment's due date as a PostgreSQL `DATE`, because it is a
  local calendar obligation rather than an instant in time.
- Store audit, creation, update, retry, and delivery timestamps as
  `TIMESTAMPTZ` in UTC.
- For a monthly recurrence whose due day does not exist in a month, use that
  month's final calendar day. This rule is implemented and unit-tested in the
  domain, not hidden in a database trigger.

### Integrity and history

- Use UUID primary keys generated by the application. Public APIs expose these
  opaque identifiers rather than database sequence values.
- Add foreign keys, `NOT NULL`, `CHECK`, and unique constraints in the database
  for every invariant it can enforce.
- Enforce exactly one occurrence for a commitment and local due date with
  `UNIQUE (commitment_id, due_date)`.
- Use explicit string status columns protected by `CHECK` constraints rather
  than PostgreSQL enum types. This keeps status changes reviewable in ordinary
  migrations.
- Add an optimistic-lock version column to mutable aggregates such as a
  commitment.
- Preserve historical financial state. Ending or pausing a commitment changes
  its status; it does not delete its occurrences. Audit events are append-only.

## Consequences

### Positive

- Amount and date handling are deterministic and safe for financial use.
- The database itself prevents common data-corruption mistakes.
- Future receipt and transaction imports can confirm an occurrence without
  rewriting what the user originally expected.
- Migrations are reproducible locally, in CI, and in production.

### Negative

- Application code must format minor units for display and validate currency
  precision at its boundary.
- Historical rows and audit data require a future retention/deletion policy.
- Optimistic-lock conflicts must be surfaced as a useful API response rather
  than silently overwriting another edit.

## Rejected alternatives

### Floating-point currency fields

Rejected because binary floating-point arithmetic can produce rounding errors.

### Storing every due date as a UTC timestamp

Rejected because a local due day such as the 31st can shift when rendered or
calculated in another time zone.

### Hard deletion of commitments

Rejected because it destroys payment history and makes the audit trail
misleading. A privacy-driven account deletion workflow is a separate future
requirement.
